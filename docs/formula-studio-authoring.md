# Formula Studio: authoring model

The primary forms describe combat behavior. JSON is the storage format, generated by the editor.
Advanced fields remain available for exact IDs, uncommon conditions, custom references, and every persisted field supported by the current V2 schema. Runtime fields generated by composition or calculation are not authored.

## Creating a calculation file

Click **+ New calculation file** in the library. Choose Character, Weapon, or Artifact, then enter its key and name. For characters, choosing a character from the list fills in the element, weapon type, talent names, and talent-data reference. Existing calculation files are disabled in this list; open those from the library to edit them.

**Create file** validates and saves a starter file, then opens it in the structured editor. Character starters include Normal Attack, Skill, and Burst groups, inherited standard inputs, and preview defaults. Add damage formulas and effects in their respective tabs. Weapon and artifact starters open with empty effect lists.

To use generated JSON, select it under **Import JSON** in the same dialog. Its contents and filename key are validated before creation. Invalid files stay in the dialog with an error, and existing files are never overwritten by creation. New files are saved under `data/damage-formulas-v2`, with weapons and artifacts in their corresponding subfolders.

Team context choices include **Hexerei count**, **Source Hexerei**, and **Recipient Hexerei**. Use these to gate Secret Rite and recipient-specific bonuses. The shared eligibility list is editable in `team-rules.json`; it does not require copying membership lists into character files. **Plunge impact** distinguishes ground-impact damage from mid-air plunge damage.

## Effect versus damage formula

A **damage formula** defines one damage instance: its name, damage type, classification, base scaling, and availability. An **effect** changes existing instances or character stats under specified conditions. Effects do not create a hit unless an equipment definition explicitly supplies extra formulas.

Use **Duplicate** beside a formula to create the next hit in an attack sequence. The copy has its own unique ID and an independent copy of all scaling terms, tags, and modifiers. For successive basic attacks, change the copied talent parameter instead of rebuilding the expression. **Remove** deletes a whole formula or talent; expression terms and other list entries also have their own removal controls. Individual property fields have no remove button.

Renaming a new or duplicated formula updates its generated ID, adding a numeric suffix when another formula already uses that ID. The advanced ID field updates immediately. Editing the ID yourself stops automatic renaming for that formula.

Weapon effects can include a **Formulas** list for separate damage procs. Use **Active Character** for a buff to the currently selected damage character, or **Active Other** for a handoff that must exclude the weapon holder. See [weapon coverage and combat assumptions](weapon-formula-coverage.md).

Dropdown changes update the affected editor section while preserving focus, scroll position, and both open and closed panels. Adding or duplicating a formula opens that new formula and keeps the existing panels in their current state.

| User supplies | Interface provides | Saved JSON |
|---|---|---|
| Damage instance name | Suggested identifier for a new hit | `label`, `id` |
| Element and damage behavior | Existing damage-type dropdown | `damageType` reference |
| Normal / Charged / Skill / Burst classification | Classification checkboxes | `tags` |
| ATK × a Skill multiplier, or another expression | Stat picker, named talent parameter picker, operators | `base` expression tree |
| Required / excluded effects | Advanced availability fields | `requiredEffects`, `excludedEffects` |
| Effect name, source, explanation | Suggested identifier for a new effect | `name`, `id`, `source`, `description` |
| Category and enabled state | Dropdown and checkbox | `category`, `defaultEnabled` |
| Trigger / assumed buff state | Common event choices plus custom reference | `activation.event` |
| Eligibility requirements | Input thresholds / team conditions | `activation.conditions` |
| Which hits change | Target presets and optional combined filters | `targets` |
| What changes and by how much | Damage layer dropdown and value builder | Modifier field and expression |

An event name documents a combat snapshot. It does not enforce uptime, consume stacks, or simulate a rotation. Conditions and required effects enforce eligibility.

## Standard and special inputs

Every character automatically has character level, Normal/Skill/Burst talent levels, constellation, combat stats, base stats, elemental/Physical damage bonuses, and enemy controls. The shared definitions come from `CharacterStandardInputsV3`; neither new characters nor support-only characters need to declare them. Formula, talent-level, and condition pickers include these inherited inputs.

The **Inputs** tab separates **Standard inputs · always available** from **Special character inputs**. Standard inputs show their references and optional preview defaults, with Reset restoring the shared value. Saved builds supply actual character values. Only special controls, such as Veils of Falsehood, Bond of Life, or combat-state toggles, need an input definition with a name, range, and starting value.

For example, a talent multiplier uses `"levelInput": "source:skillTalentLevel"` automatically. A constellation requirement can reference `source:constellation`. A custom stack expression uses `local:veilStacks`. Character JSON stores only special definitions in `inputs`; optional standard preview overrides go in `inputDefaults`, such as `{"skillTalentLevel": 10}`. Legacy input ID aliases remain supported through `statBindings`, without redefining the standard input.

## Pale Hymn, step by step

1. Open `lauma.json`, select **Effects**, and click **Add Effect**.
2. Enter **Pale Hymn**, source **Lauma · Elemental Burst**, and the assumed-state description. Choose **Team** and enable the default checkbox. The editor proposes an ID; existing IDs stay stable.
3. Choose **Buff active** as the trigger.
4. Under **Damage changes**, add a modifier. Choose **Lunar-Bloom hits** under **Applies to** to reproduce the example, or **All Lunar damage** for the broader scope requested earlier.
5. Add **Base addition**. Under **Value comes from**, choose **Multiply**.
6. Set term 1 to **Character stat or input → Lauma Elemental Mastery**.
7. Set term 2 to **Talent multiplier → Lauma → Elemental Burst → Lunar-Bloom DMG Increase**. The matching Burst-level input is suggested; verify it reads **Lauma Burst level**.
8. Validate, then save.

The user picks named concepts. The editor writes `input: laumaElementalMastery`, `characterKey: lauma`, `talent: combat3`, `parameter: param4`, `levelInput: laumaBurstTalentLevel`, and the `multiply` / `operands` structure.

The example target saves as `requiredTags: [lunarBloom]`. **All Lunar damage** saves as `damageKinds: [lunar]`. These are different scopes; the editor does not silently replace one with the other.

## Changing a modifier

**What changes?** can switch an existing modifier between:

| Choice | Storage | Amount |
|---|---|---|
| Base addition | `base` | Flat expression |
| Base damage bonus | `baseDamageBonus` | Contribution with expression and units |
| Independent base multiplier | `baseDamageMultiplier` | Each contribution supplies a separate `(1 + percentage)` factor |
| Damage bonus | `damageBonus` | Contribution |
| Post-bonus addition | `postBonusBase` | Flat expression |
| DEF reduction / ignore | `defenseMitigation.reduction` / `.ignore` | Contribution |
| Bypass DEF | `defenseMitigation.bypass` | Checkbox |
| RES reduction | `resistanceMitigation.reduction` | Contribution |
| CRIT Rate / CRIT DMG | `crit.additionalRate` / `.additionalDamage` | Contribution |
| Elevation | `elevation` | Contribution |

Changing a layer moves the existing expression to the new field and removes the old field. Flat-to-percentage conversions introduce an explicit unit selector; they do not rescale numeric values automatically. **Percentage points** means 20 is +20%; **ratio** means 0.2 is +20%. Review the amount after switching.

A modifier may contain multiple damage changes sharing the same targets and conditions. Add separate modifiers when those targets or conditions differ.

## Weapon infusions

Add a **Weapon infusion** damage change to an effect modifier, choose a shared
ordinary talent damage type, and select the eligible weapon types. Target the
Normal/Charged/Plunging classifications that the infusion affects and set the
recipient as for other buffs. Infusion changes the element before damage-bonus,
resistance, and reaction selection; it preserves the hit's ID and scaling.

Each formula has **External weapon infusion**: allow on physical attacks (the
default), allow overriding its existing element, or cannot be overridden. Mark
protected personal conversions with the last choice. Bow/Catalyst eligibility is
separate from elemental damage bonuses. Priorities describe a combat snapshot;
weapon-gauge reactions, infusion refresh timing, and rotations are not simulated.
Conflicting different infusions with equal priority produce a validation error
when that combination is calculated rather than choosing an arbitrary element.

Saved modifier data uses `infusion: {damageType, weaponTypes, priority}`; formula
protection uses `infusionRule`. The calculated result reports the effective damage
type and `infusionSourceEffectId`. Bennett C6 uses this system for melee attacks;
its separate Pyro damage stat bonus reaches all weapon types inside his field.
The **Bennett C6 · Pyro infusion** input checkbox can disable conversion while
leaving that separate stat bonus active. It cannot bypass the field or C6 requirements.

## Choosing shared damage types

On each talent damage instance, choose **Damage type** from the shared catalog. You do not define types separately for each character. **Edit shared damage types** opens `damage-types.json`, where forms configure element, kind, DEF handling, CRIT, bonus eligibility, and optional built-in scaling. Saving a shared type updates all hits that use it; validation prevents removing an in-use type.

The character file stores only the selection, such as `"damageType": "directPyro"`. Its base scaling and Normal/Charged/Skill/Burst tags remain specific to the hit. Shared types describe how damage is processed, not which talent multiplier or attack classification it uses. Standard source-stat references are resolved for each character. A different-element hit uses that element's bonus and enemy resistance automatically.

## Expressions and advanced controls

Value sources include fixed numbers, named character inputs, named talent multipliers, highest team stats, and equipment/team context. Operators include addition, multiplication, division, minimum (cap), and maximum (floor). Nest these to express mixed scaling or capped bonuses.

Talent labels come from bundled character data; exact `paramN` identifiers remain visible for disambiguation. Missing labels retain their IDs. Explicit support talent tables also remain selectable. The selected talent-level input determines the multiplier at calculation time.

Advanced fields cover stat conversions and phases, constellation requirements, per-change conditions, effect dependencies, stacking groups and priority, metrics, custom tags, input ranges and units, saved-build sources, and equipment recipients / piece thresholds. Unknown existing data is preserved when editing another field. Validation remains necessary for references involving selected teammates and equipment.

Independent base multipliers apply after the existing base calculation, including
flat base additions. A 20% contribution means ×1.2, not ×0.2. Multiple matching
contributions multiply separately. Use one Add expression to group percentages
inside a single independent factor. Post-bonus additions are not multiplied.

## Unified character recipients

Character files use authoring schema 3. There is one entry per character; **Support only** means personal damage formulas have not been authored yet.

Each effect has a Default recipient: Self, Whole party, Other party members, Active character, or Enemy debuff. Each damage change and stat change can override that default, and can exclude the source. Use Self for source control changes; use recipient stat targets for party buffs. Mixed effects such as Citlali C2 are one effect with separate recipient choices on their components.

Value pickers distinguish inherited standard inputs, **Source character**, **Buff recipient**, and local character controls. They save `source:<stat>`, `recipient:<stat>`, and `local:<id>` respectively; shared enemy controls use `battle:<id>`. Talent multipliers use this character's table and inherited talent-level input. Runtime namespacing and character build binding happen automatically. The selected damage character is assumed to be on field.

### Direct Stellar-Conduct

Select shared damage type `stellarConductElectro` for Electro Stellar-Conduct
hits. The structured editor offers **Stellar damage** and **All Stellar damage**
selectors. This kind bypasses DEF and ordinary elemental/common damage bonuses,
can CRIT, and supplies the Stellar EM bonus automatically.

For the current field's reaction multiplier, use an independent base percentage
(`baseDamageMultiplier`: multiplier minus one). Stellar additive reaction damage,
such as Cyno's 600% EM addition, belongs in **After-bonus flat damage**
(`postBonusBase`), so it is added after the reaction bonus and before CRIT/RES.
See `cyno.json` and the shared `damage-types.json` for working examples.
